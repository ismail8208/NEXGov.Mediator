# Compatibility Policy

**This document describes the MediatR compatibility baseline for
NEXMediator V1** — see
[`docs/PRODUCT-DIRECTION.md`](./PRODUCT-DIRECTION.md) for how that
baseline relates to NEXMediator's own, independent product identity and
future development. It does not imply that all future MediatR changes
are automatically required or adopted; the baseline is pinned to the
upstream commit recorded in [`docs/UPSTREAM-AUDIT.md`](./UPSTREAM-AUDIT.md),
not to MediatR "in general."

NEXGov.Mediator (product name: NEXMediator) targets a **source-compatible
baseline with MediatR** for a defined, supported API surface. For most of
that surface, source compatibility means an application using a supported
pattern should be able to change:

```csharp
using MediatR;
```

to:

```csharp
using NEXGov.Mediator;
```

with no further code changes, for the members and usage patterns this
library declares as supported. **This is not true of the entire surface**:
the DI bootstrap identity is an intentional, deliberate NEXMediator
product-identity decision, not a compatibility gap —

| MediatR | NEXMediator |
|---|---|
| `AddMediatR(...)` | `AddNEXMediator(...)` |
| `MediatRServiceConfiguration` | `NEXMediatorServiceConfiguration` |
| `MediatRServiceCollectionExtensions` | `NEXMediatorServiceCollectionExtensions` |

— so migrating an application that uses these members also requires
renaming the DI bootstrap call (and, if referenced directly, the
configuration type) alongside the namespace change. See the README's
Migration guidance for the complete, accurate step list. Every other row
in the matrix below still uses its MediatR-matching name, since only the
DI bootstrap identity was deliberately diverged.

## Ground rules

1. **Clean-room implementation.** No MediatR source code is copied,
   adapted, or referenced. Compatibility is achieved by independently
   implementing equivalent public API shapes and behavior.
2. **No compatibility claim without a test.** An API family is not
   considered behaviorally compatible until a test in
   `tests/NEXGov.Mediator.CompatibilityTests` exercises it and passes.
   Appearing in this matrix as "V1 Required" or "V1 Extended" states
   *intent*, not a completed guarantee — see the Status column.
3. **Public shape first, internals independent.** Method signatures,
   type names, and namespaces follow the supported surface for the V1
   baseline — with one deliberate, documented exception (the DI bootstrap
   identity: `AddNEXMediator`/`NEXMediatorServiceConfiguration`/
   `NEXMediatorServiceCollectionExtensions`, see above) — while internal
   implementation is free to differ from MediatR entirely.
4. **Additive, incremental delivery.** Each API family is implemented in
   its own tracked unit of work. This document is updated as each family
   moves between classifications.

## Classification legend

| Classification | Meaning |
|---|---|
| **V1 Required** | Part of the minimum surface needed for common MediatR usage patterns (request/response dispatch, handlers, DI registration). Targeted for the first compatible release. |
| **V1 Extended** | Common but secondary surface (pre/post processors, exception handling, streaming). Targeted for the first compatible release after the required surface is stable. |
| **Later** | Valid MediatR surface that NEXGov.Mediator intends to support eventually, but is not targeted for V1. |
| **Out of Scope** | Not planned for support, or intentionally excluded (e.g., legacy/obsolete MediatR members). |

## Status legend

| Status | Meaning |
|---|---|
| **Not started** | No implementation exists yet. |
| **In progress** | Implementation exists but is not yet covered by compatibility tests. |
| **Verified** | Covered by passing tests in `NEXGov.Mediator.CompatibilityTests`. |
| **Verified (API contract only)** | The public type/method shape (name, signature, generics, constraints) is covered by passing reflection-based tests, but no runtime dispatch/execution behind it exists yet. Used for members like `CreateStream(...)` whose interface shape can be verified independently of the mediator runtime that will eventually call them. Do not treat this as a behavioral compatibility guarantee. |
| **Verified (basic runtime)** | Both the public API shape and a first, real runtime implementation are covered by passing tests (handler resolution via `IServiceProvider`, dispatch to the correct handler, `CancellationToken` propagation, deterministic failure on missing/ambiguous handlers). Does not imply the full MediatR feature set around that member is present — see the row's Notes for what remains outstanding. |

Generic constraints are enforced naturally by `Type.MakeGenericType` throwing `ArgumentException` on an invalid closure, which is caught and treated as "no registration for this candidate" — narrower than current source's own broader `catch (Exception)`, a deliberate, documented scope-narrowing consistent with this project's established policy of catching only the specific exception a given failure mode is verified to throw. **Never discovers a `RegisterGenericHandlers`-synthesized closed request instantiation** — `Assembly.DefinedTypes` only ever yields a generic request type's own open definition, never a closed type `MakeGenericType` produced at registration time — a verified limitation matching current source's own identical algorithm shape, not a NEXGov-specific defect. **Never applies to a void (non-generic `IRequest`) request** — `DiscoverRequestResponsePairs` only ever finds `IRequest<TResponse>` implementers, so a void request structurally can never appear as a candidate — also matching current source. **Never applies to `IStreamPipelineBehavior<,>`** — verified no equivalent pass exists for `StreamBehaviorsToRegister` in current source's `AddRequiredServices`, confirmed by a dedicated regression test; `AddOpenStreamBehavior`/`StreamBehaviorsToRegister` rely solely on ordinary DI generic closing, unchanged. **Lifetime:** every generated closed registration uses the specific `AddOpenBehavior`/`AddBehavior` call's own `ServiceDescriptor.Lifetime` (not `NEXMediatorServiceConfiguration.Lifetime`), verified against current source. **Duplicates:** `services.TryAddEnumerable(...)`, deduplicating by `(ServiceType, ImplementationType)` — a third distinct duplicate policy in this project, compared to `GenericHandlerRegistrar`'s/`OpenGenericHandlerRegistrar`'s always-`AddTransient`. **Ordering:** the open-registration `TryAddEnumerable` call and the nested-generic-response closing pass are interleaved per `BehaviorsToRegister` entry, in one pass (not two separate passes over the whole list) — required to preserve correct relative pipeline position when a triggering entry is mixed with ordinary behaviors registered before/after it, verified against current source's own single-loop structure. **Deliberate, documented safety deviation (Category B, consistent with MED-013/MED-022 policy):** current source always *also* keeps the bare open `BehaviorsToRegister` registration for a triggering entry, alongside its generated closed ones. This implementation omits that bare open registration instead — empirically verified, current source's own structure is crash-prone here: Microsoft.Extensions.DependencyInjection's native open-generic closing has two distinct failure modes for this shape — a naive positional substitution that also happens to violate a generic *constraint* on the implementation is gracefully suppressed (silent skip) when resolved via `GetServices<T>()`, but a naive substitution that is merely *structurally* mismatched (constructs successfully, but the resulting closed type does not actually implement the requested closed service interface — the common case for an unconstrained response type parameter) is **not** suppressed; it throws an uncaught `ArgumentException` straight out of Microsoft.Extensions.DependencyInjection's own `ConstructorCallSite` the moment anything resolves the pipeline for that request. Omitting the bare open registration for a triggering entry avoids this crash and changes no other observable behavior, since that registration was otherwise either permanently inert or actively crash-inducing depending on constraint happenstance — verified by dedicated regression test (`OrdinaryOpenRegistration_Alone_CannotResolveNestedGenericResponseBehavior`, confirming the throw current source's own structure would hit). Implemented in MED-024. |
