# Compatibility Policy

NEXGov.Mediator aims to be a **source-compatible alternative to MediatR** for a
defined, supported API surface. Source compatibility means an application
using a supported pattern should be able to change:

```csharp
using MediatR;
```

to:

```csharp
using NEXGov.Mediator;
```

without further code changes, for the members and usage patterns this
library declares as supported.

## Ground rules

1. **Clean-room implementation.** No MediatR source code is copied,
   adapted, or referenced. Compatibility is achieved by independently
   implementing equivalent public API shapes and behavior.
2. **No compatibility claim without a test.** An API family is not
   considered behaviorally compatible until a test in
   `tests/NEXGov.Mediator.CompatibilityTests` exercises it and passes.
   Appearing in this matrix as "V1 Required" or "V1 Extended" states
   *intent*, not a completed guarantee — see the Status column.
3. **Public shape first, internals independent.** Method signatures,
   type names, and namespaces follow the supported surface; internal
   implementation is free to differ from MediatR entirely.
4. **Additive, incremental delivery.** Each API family is implemented in
   its own tracked unit of work. This document is updated as each family
   moves between classifications.

## Classification legend

| Classification | Meaning |
|---|---|
| **V1 Required** | Part of the minimum surface needed for common MediatR usage patterns (request/response dispatch, handlers, DI registration). Targeted for the first compatible release. |
| **V1 Extended** | Common but secondary surface (pre/post processors, exception handling, streaming). Targeted for the first compatible release after the required surface is stable. |
| **Later** | Valid MediatR surface that NEXGov.Mediator intends to support eventually, but is not targeted for V1. |
| **Out of Scope** | Not planned for support, or intentionally excluded (e.g., legacy/obsolete MediatR members). |

## Status legend

| Status | Meaning |
|---|---|
| **Not started** | No implementation exists yet. |
| **In progress** | Implementation exists but is not yet covered by compatibility tests. |
| **Verified** | Covered by passing tests in `NEXGov.Mediator.CompatibilityTests`. |
| **Verified (API contract only)** | The public type/method shape (name, signature, generics, constraints) is covered by passing reflection-based tests, but no runtime dispatch/execution behind it exists yet. Used for members like `CreateStream(...)` whose interface shape can be verified independently of the mediator runtime that will eventually call them. Do not treat this as a behavioral compatibility guarantee. |
| **Verified (basic runtime)** | Both the public API shape and a first, real runtime implementation are covered by passing tests (handler resolution via `IServiceProvider`, dispatch to the correct handler, `CancellationToken` propagation, deterministic failure on missing/ambiguous handlers). Does not imply the full MediatR feature set around that member is present — see the row's Notes for what remains outstanding. |

| `AddMediatR(...)` | V1 Required | Verified | Two extension methods on `IServiceCollection` in namespace `Microsoft.Extensions.DependencyInjection` (`AddMediatR(Action<MediatRServiceConfiguration>)` and `AddMediatR(MediatRServiceConfiguration)`), verified against current source. Both return the same `IServiceCollection` instance; both throw `ArgumentNullException` for a null `services`/`configuration` argument (a reasonable, documented inference — current MediatR has no explicit null-guards there and would fail via an incidental `NullReferenceException`/framework-thrown exception deeper in the call chain instead) and `ArgumentException` when no assembly was configured to scan (message verified against current source). Registers `IMediator`/`ISender`/`IPublisher` (via `TryAdd`, so a consumer's own registration — before or after calling `AddMediatR` — always wins) and scans the configured assemblies. Scanning behavior differs by family, verified against current source: **request handlers** (`IRequestHandler<,>`/`IRequestHandler<>`) — exactly one concrete implementation per closed request type is registered (`TryAddTransient`; duplicates are silently ignored, first-discovered wins); **notification handlers** and **exception handlers/actions** (`INotificationHandler<>`, `IRequestExceptionHandler<,,>`, `IRequestExceptionAction<,>`) — every matching implementation is registered (`AddTransient`, never `TryAdd`), and for exception handlers/actions specifically, the corresponding `RequestExceptionProcessorBehavior<,>`/`RequestExceptionActionProcessorBehavior<,>` is **automatically inserted into the pipeline** if any matching implementation was found (their relative order controlled by `RequestExceptionActionProcessorStrategy`); **pre/post processors** (`IRequestPreProcessor<>`/`IRequestPostProcessor<,>`) — only scanned/registered as services when `AutoRegisterRequestProcessors` is set `true` (default `false`), and even then the corresponding `RequestPreProcessorBehavior<,>`/`RequestPostProcessorBehavior<,>` is **not** automatically inserted into the pipeline — that requires the explicit `AddRequestPreProcessor`/`AddRequestPostProcessor` methods introduced in MED-011 (see their rows); **pipeline behaviors** (`IPipelineBehavior<,>`) are never scanned at all, matching current MediatR — only explicit `AddBehavior`/`AddOpenBehavior` registration inserts one; **stream request handlers** (`IStreamRequestHandler<,>`) are not scanned — that contract/runtime is not implemented in this project yet (see the streaming rows). Abstract classes, interfaces, and any type containing open generic parameters are always excluded from this scanning; a type containing open generic parameters is included only for the two request-handler families, and only when `RegisterGenericHandlers = true` — see the MED-013 note below. Implemented in MED-010. **Indirect implementation discovery (MED-012):** scanning finds a closed service interface implemented indirectly — through an abstract or non-abstract base class, or through a custom interface that itself extends the open service interface, at any inheritance depth in either direction — exactly as well as one implemented directly, for every scanned family (`IRequestHandler<,>`, `IRequestHandler<>`, `INotificationHandler<>`, `IRequestExceptionHandler<,,>`, `IRequestExceptionAction<,>`, `IRequestPreProcessor<>`, `IRequestPostProcessor<,>`) and for `AddBehavior`/`AddOpenBehavior`. This rests on `Type.GetInterfaces()` returning the full transitive closure of implemented interfaces (verified empirically against .NET reflection, not assumed) — a fact this project's own scanning code already relied on since MED-010, but which an earlier revision of an internal helper's doc comment inaccurately described as "direct interfaces only." `Type.GetInterfaces()` also already deduplicates a closed interface reachable via more than one path (e.g. two sibling interfaces both extending the same open interface), so such a type registers exactly one descriptor, not two. An **abstract** type is still never itself registered as an implementation, whether or not it implements the closed interface directly — only its concrete (non-abstract) descendants are candidates. **Generic request-handler registration (MED-013):** with `RegisterGenericHandlers = true`, an open-generic, concrete `IRequestHandler<,>`/`IRequestHandler<>` implementation is expanded into one closed registration per valid combination of candidate types satisfying its own generic-parameter constraints (`class`, `struct`, a base type, an interface, `new()`, and `notnull` — the last has no reflectable runtime representation and so imposes no additional filtering, verified against current source) — reproducing current MediatR's own observable algorithm (verified directly against current source, not assumed or copied), scoped to request handlers only: notification handlers, exception handlers/actions, and pre/post processors containing open generic parameters remain excluded regardless of this setting, a deliberate narrowing of current MediatR's own broader (and, per source, `RegisterGenericHandlers`-gated across every scanned family) behavior. Closing-candidate types are scanned only from the configured `AssembliesToRegister` (never AppDomain-wide), are always concrete classes — a value type can never satisfy a `where T : struct` parameter this way, since the candidate pool itself is class-only, verified against current source — and are never filtered by `TypeEvaluator` (which applies only to the handler implementation type itself, not to the types later used to close it). The response type for each closed registration is read from the closed request type's own `IRequest<TResponse>` implementation, not tracked positionally through the handler, so `Handler<TEntity,TId> : IRequestHandler<Get<TEntity,TId>, Result<TEntity>>`-style handlers (where the response references only some of the handler's parameters) work correctly; a handler whose own generic-parameter constraint references another of its *own* parameters (e.g. `where TEntity : IEntity<TCategory>`) cannot be resolved by the independent per-parameter matching this algorithm uses (verified empirically: `Type.IsAssignableFrom` against a constraint that still contains an unresolved sibling parameter is always `false`) and simply produces no registrations for that handler, not an error. A handler whose base class fixes only *some* of a multi-argument request type's own generic arguments (leaving the rest to the derived handler) is closed positionally from the *declaring* handler's own `GetGenericArguments()`, so this shape produces no registration when the handler's remaining arity no longer matches the request type's total arity — a verified, faithfully-replicated limitation of the underlying algorithm. Generated closed registrations always use `AddTransient` (never `TryAddTransient`, even though ordinary non-generic request-handler scanning does) and are always `ServiceLifetime.Transient` regardless of `MediatRServiceConfiguration.Lifetime` — both verified against current source — so a consumer's own manual registration for the same closed service does not automatically "win" the way it does against an ordinary scanned handler; whichever registration is last in the provider wins on resolution, exactly like any other duplicate MEDI service registration. `MaxGenericTypeParameters`/`MaxTypesClosing`/`MaxGenericTypeRegistrations` throw `ArgumentException` when exceeded, each independently, evaluated once per handler/interface pair; `MaxGenericTypeParameters = 0` and `MaxTypesClosing = 0` each genuinely disable their own check, but — **verified quirk, faithfully replicated, not a defect introduced here** — the `MaxGenericTypeRegistrations` check is gated on `MaxGenericTypeParameters > 0` in current source, not on `MaxGenericTypeRegistrations > 0`: setting `MaxGenericTypeParameters = 0` therefore also disables the registrations-count check even if `MaxGenericTypeRegistrations` is left at a real value, while setting only `MaxGenericTypeRegistrations = 0` does *not* disable that check — it inverts it, since the check becomes `totalCombinations > 0`, true for almost any non-empty candidate set. `RegistrationTimeout` (milliseconds) similarly does **not** mean "disabled" at `0` — verified against current source, it is passed directly to `CancellationTokenSource(int)`, whose documented contract treats `0` as already-expired, so generic handler registration is cancelled immediately and a `TimeoutException` is thrown; only `-1` (`Timeout.Infinite`) truly disables it. One deliberate safety deviation from current source, in both directions documented here for transparency: a generic handler whose own type parameter is unused by its service contract (e.g. `Handler<T> : IRequestHandler<Ping, Pong>`, where `Ping`/`Pong` are already fully closed) reaches `Type.GetGenericTypeDefinition()` on a non-generic type in current source, which throws uncaught and would crash the consumer's whole `AddMediatR` call; a candidate satisfying a parameter's base/interface constraints but not its `new()` constraint is similarly let through to an uncaught `Type.MakeGenericType` failure in current source. This implementation recognizes both shapes ahead of time and treats them as "not closable," skipping rather than crashing — the observable difference is a missing registration (which, absent `RegisterGenericHandlers`, is already how a consumer would experience a handler they forgot to write) instead of an unhandled exception during DI container construction. Implemented in MED-013. |

## Explicitly out of scope (for now)

Nothing in the current matrix is classified Out of Scope. Members MediatR
has deprecated or removed in its own history, and any surface not listed
above, are treated as **Later** until a deliberate decision is recorded
here.

## Updating this document

When an API family's implementation begins or its test coverage changes,
update its row's **Status** column in the same change that alters the
code. Classification changes (e.g., promoting something from *Later* to
*V1 Extended*) should be called out explicitly in the change description.
